## Anatomy

```tsx
<Workflow
  steps={[
    { id: "start", label: "Start", state: "completed" },
    { id: "configure", label: "Configure", state: "completed" },
    { id: "review", label: "Review" },
    { id: "finish", label: "Finish", optional: true },
  ]}
  currentStepId={currentStepId}
  onStepChange={({ step }) => setCurrentStepId(step.id)}
/>
```

For custom layouts, mount compound children explicitly:

```tsx
<Workflow steps={steps} currentStepId={id}>
  <Workflow.Progress />
  <Workflow.List>
    {steps.map((s) => (
      <Workflow.Step key={s.id} stepId={s.id} />
    ))}
  </Workflow.List>
  <Workflow.Nav />
</Workflow>
```

## Data model

```ts
type WorkflowStepState = "pending" | "current" | "completed" | "error";

interface WorkflowStep {
  id: string;
  label: string;
  description?: string;
  state?: WorkflowStepState;
  optional?: boolean;
  disabled?: boolean;
  meta?: Record<string, unknown>;
}
```

- **Identity is consumer-owned.** Ids are opaque strings; duplicates throw at ingest.
- **`currentStepId` overrides matching steps' state with `"current"`** at runtime so consumers can pass a mix of `completed` / `pending` / `error` values and forget about maintaining `"current"` on individual steps.
- **`optional` and `disabled`** are visual / behavioral hints. `disabled` steps skip focus and refuse activation.

## Orientation

`orientation` accepts `"horizontal"` (default) or `"vertical"`. Arrow-key nav follows the axis:

- Horizontal: `ArrowLeft` / `ArrowRight` (RTL swaps).
- Vertical: `ArrowUp` / `ArrowDown`.

Orthogonal arrow keys are no-ops.

## Navigation model

`navigationMode` is a **hint** exposed through context — the runtime never blocks navigation.

- `"linear"` — the consumer prefers strict forward progression; the value is available for custom renderers that want to style unreachable steps.
- `"non-linear"` — no ordering hint; every enabled step is navigable.

`onCurrentStepChange` fires whenever the current step id changes.
`onStepClick` fires on every click, even when the clicked step is
already current. `onStepChange` emits the richer step payload for
consumers that want full step metadata. `onNavigate` fires on
`Workflow.Nav` button clicks (`direction: "next" | "previous"`).

## Progress

Enable `showProgress` to render a `role="progressbar"` bar ahead of the list. The bar fills to `completed / total` percent — disabled steps are excluded from the total.

## Keyboard model

| Key                       | Action                                     |
| ------------------------- | ------------------------------------------ |
| Arrow keys (axis-aligned) | Move focus to previous / next enabled step |
| `Home` / `End`            | Jump to first / last enabled step          |
| `Enter` / `Space`         | Activate the focused step                  |
| Orthogonal arrow keys     | No-op (focus stays put)                    |

## Accessibility

- Root exposes `role="group"` with `aria-label` fallback.
- List uses `role="list"`; each step wrapper is `role="listitem"` with `aria-posinset` / `aria-setsize`.
- Steps are native `<button>` elements. The current step carries `aria-current="step"` (the WAI-ARIA idiomatic pattern for stepper interfaces).
- Connectors are decorative `aria-hidden="true"`.
- Single `aria-live="polite"` announcer speaks step transitions.

## Non-goals

- No workflow engine.
- No business-rule execution.
- No persistence.
- No enforced linear-only progression.
- No hard-coded step catalog.

## Controlled state

- `currentStepId` + `onCurrentStepChange` — the active step pointer.
- `focusedStepId` + `onFocusedStepChange` — the roving focus pointer.

Both can be omitted to let the stepper own that slice; both control
modes compose freely.

## Performance guidance

- Step counts above a few dozen are the exception, not the rule. The
  component is not virtualized; the full step list renders in the DOM.
- `resolveStepStates` runs once per render and is linear in the step
  count. Memoize `steps` across renders if the array identity would
  otherwise change on every parent render.
- `showProgress` adds a single DOM node (`role="progressbar"`); the
  cost is negligible even for long workflows.

## Backend independence

The stepper visualizes a workflow — it does not execute one.

- `steps` is plain data. Compute it from any state container; the
  stepper reads only `label`, `state`, `optional`, `disabled`,
  `description`, and `meta`.
- `navigationMode="linear"` is a **hint**, not a gate — the runtime
  never blocks a click. Consumers who need strict forward-only
  progression apply their own guard inside `onCurrentStepChange`.
- `onNavigate` fires on the `Workflow.Nav` buttons; `onStepClick`
  fires on every step click (even the current step);
  `onCurrentStepChange` fires only when the current step id would
  change; `onStepChange` emits the full step payload.

## Package boundary

`Workflow` ships only in `@kairoui-pro/workflow`. The free tier offers
`@kairoui/core`'s [`Progress`](/components/core/progress) component for
single-bar progress and
[`Timeline`](/components/core/timeline) for linear event histories,
but no stepper. The Pro package re-uses `@kairoui/core` focus
primitives and `@kairoui/hooks` identity helpers; nothing is duplicated.

## API and DX gaps

- `onCurrentStepChange` and `onStepChange` intentionally coexist (id-only
  vs payload-rich) but can look redundant at first glance.
- `navigationMode` is advisory by design. Teams expecting hard gating
  must implement their own guard logic.
- The `Workflow.Step` slot currently has less generated metadata than
  root-level APIs due export aliasing (`WorkflowStepComponent`).
