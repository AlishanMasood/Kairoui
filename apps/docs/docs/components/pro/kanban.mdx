    { id: "audit", columnId: "backlog", title: "Review audit findings", order: 0 },

## Anatomy

```tsx
<Kanban
  columns={columns}
  cards={cards}
  onCardMove={({ card, toColumnId, toIndex, order }) => reorder(card.id, toColumnId, order)}
  onColumnMove={({ column, toIndex, order }) => reorderColumn(column.id, order)}
  onCardClick={({ card }) => openCardDetail(card.id)}
/>
```

For custom layouts, mount compound children explicitly:

```tsx
<Kanban columns={columns} cards={cards}>
  <Kanban.Board>
    {columns.map((c) => (
      <Kanban.Column key={c.id} columnId={c.id} />
    ))}
  </Kanban.Board>
  <Kanban.CardTemplate render={({ card }) => <MyCard card={card} />} />
</Kanban>
```

## Data model

```ts
interface KanbanColumn {
  id: string;
  title: string;
  order?: number;
  meta?: Record<string, unknown>;
}

interface KanbanCard {
  id: string;
  columnId: string;
  title: string;
  description?: string;
  order?: number;
  meta?: Record<string, unknown>;
}
```

- **Identity is consumer-owned.** The Kanban never mints ids. Duplicate ids or unknown `columnId` references throw at ingest.
- **Ordering is consumer-authoritative.** When every card / column carries `order`, they sort ascending; otherwise the input array order wins.
- **Persistence is consumer-owned.** The Kanban stores nothing internally. Every move fires a callback; the consumer applies the change and the new `cards` / `columns` flow back through props.

<Callout type="warning" title="No hard-coded statuses">
  The Kanban ships no `"todo"` / `"doing"` / `"done"` presets. Columns are whatever the consumer
  passes.
</Callout>

## Keyboard model

Drag/drop is **not** the only interaction method. Every drag gesture has a keyboard equivalent.

| Key                        | Action                                         |
| -------------------------- | ---------------------------------------------- |
| `ArrowUp` / `ArrowDown`    | Move focus within a column                     |
| `ArrowLeft` / `ArrowRight` | Move focus to sibling column                   |
| `Home` / `End`             | First / last card in column                    |
| `Ctrl+Home` / `Ctrl+End`   | First card of first / last column              |
| `Enter` / `F2`             | Fire `onCardClick`                             |
| `Space`                    | Pick up card for keyboard move                 |
| Arrows during move         | Update insertion index                         |
| `Space` during move        | Commit (fires `onCardMove`)                    |
| `Escape` during move       | Cancel                                         |
| `Delete` / `Backspace`     | Fire `onCardDelete` when the consumer wires it |

The column header supports pickup with `Space`, movement with arrows,
commit with `Space`, and cancel with `Escape`.

## Callbacks

| Callback            | Payload                                                         |
| ------------------- | --------------------------------------------------------------- |
| `onCardClick`       | `{ card, column, nativeEvent }`                                 |
| `onCardMove`        | `{ card, fromColumnId, fromIndex, toColumnId, toIndex, order }` |
| `onColumnMove`      | `{ column, fromIndex, toIndex, order }`                         |
| `onDrop`            | `{ card, fromColumnId, fromIndex, toColumnId, toIndex }`        |
| `onSelectionChange` | `KanbanSelection` (none / card / column)                        |
| `onCardDelete`      | `TCard`                                                         |

`order` is computed via `nextOrderBetween(before, after)` — consumers with a monotonic order key can persist it directly.

## Empty columns

An empty column is a first-class drop target with its own `aria-label`. Consumers render a
placeholder via `renderEmptyState` or `<Kanban.EmptyState>`.

## Accessibility

- Root exposes `role="application"` + `aria-roledescription="Kanban board"`.
- Board is `role="list"`; column bodies are `role="list"`.
- Cards render inside `role="listitem"` wrappers that carry `aria-posinset` /
  `aria-setsize`; the card action itself is a `<button>` with
  `aria-roledescription="Card"` and `aria-pressed` for selection.
- A single `aria-live="polite"` announcer speaks pickup / over / drop / cancel events.
- All bindings honor `prefers-reduced-motion`.

## Locale and RTL

- `locale` — BCP 47 tag consumed by any card metadata (consumer controls this through `renderCard`).
- `dir="rtl"` — flips the visual column layout. Arrow-key semantics for horizontal moves swap accordingly.

## Non-goals for v1

- No project-management workflow (no swim-lanes / WIP limits / assignees).
- No persistence — moves fire callbacks; the consumer owns storage.
- No hard-coded status presets.
- No card content library — the consumer renders card bodies.
- Drag/drop is not required — every gesture has a keyboard equivalent.

## Controlled state

Every stateful concern is controllable:

- `selection` + `onSelectionChange`
- `focusedCardId` + `onFocusedCardChange`
- `focusedColumnId` + `onFocusedColumnChange`

Omit a controlled value to let the Kanban own that slice.

## Performance guidance

- Set `virtualizeCards` + `cardHeight` on columns that routinely exceed
  roughly 50 cards. The windowing walks the DOM for the viewport only.
- Set `virtualizeColumns` + `columnWidth` for boards with more than
  roughly 15 columns — horizontal virtualization reuses the same
  `computeVirtualizedRange` helper as `@kairoui/hooks`.
- `partitionCardsByColumn` runs once per render and is linear in the
  card count. Memoize `cards` across renders.
- `nextOrderBetween(before, after)` is a midpoint helper — a monotonic
  `order` key avoids re-indexing when a card moves. Consumers who store
  the raw index must rewrite neighboring cards on every move.

## Backend independence

The Kanban ships zero backend adapters.

- Columns and cards are plain data. Fetch, store, and persist with
  whatever stack you prefer.
- The Kanban never mints ids. Duplicates or dangling `columnId`
  references throw at ingest — a loud failure rather than silent data
  corruption.
- `onCardMove` / `onColumnMove` fire plain-data payloads with
  `fromIndex` / `toIndex` / `order` so persistence maps one-to-one onto
  the consumer's write path. The Kanban does not debounce or batch.
- `dropAcceptance` is a predicate — the consumer decides whether a
  particular drop is legal (per-user permissions, cross-board moves,
  etc.). The Kanban enforces nothing.

## Package boundary

`Kanban` ships only in `@kairoui-pro/kanban`. The free tier does not
include a board component. The Pro package re-uses
`@kairoui/core` collection primitives, `@kairoui/hooks` focus
helpers, and `@kairoui/utils` identity assertions; nothing is
duplicated.

## API and DX gaps

- Ordering is intentionally consumer-owned. Apps without stable order
  keys must design their own rebalance strategy.
- The keyboard drag model is powerful but has a larger mental model
  than pointer-only boards.
- Horizontal and vertical virtualization are opt-in and require sizing
  discipline (`columnWidth`, `cardHeight`) from consumers.
